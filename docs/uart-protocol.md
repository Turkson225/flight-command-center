# Nano ↔ ESP32 UART protocol v1 (proposed)

**Status:** Integration contract and host-side reference codec only. No Nano flight-control or ESP32 sensor firmware has been loaded or tested by this repository. Before connecting to aircraft control, validate on a bench with independent output measurement and fault injection.

## Physical interface

Use a shared ground, TTL UART, 57,600 baud, 8 data bits, no parity, one stop bit (`57600 8N1`). Nano TX at 5 V must be shifted to a safe ESP32 3.3 V RX level; never connect it directly. Confirm the ESP32 TX to Nano RX logic level or use a suitable bidirectional level shifter. The classic Nano's D0/D1 hardware UART also serves USB upload/debug; isolate the link during programming and do not interleave debug `Serial.print` text into framed traffic. Select ESP32 UART pins appropriate to the actual module and wiring. Do not connect RS-232 voltage levels.

## Framing and checksum

One ASCII frame per line:

```text
$<payload>*<CRC16><LF>
```

- A payload begins `FD1,TYPE`; `FD1` is the exact major wire version. Unknown versions/types are rejected rather than guessed.
- `<CRC16>` is exactly four **uppercase hexadecimal** digits. Compute CRC-16/CCITT-FALSE over the ASCII bytes of `<payload>` only: polynomial `0x1021`, init `0xFFFF`, no reflection, XOR out `0x0000`. Standard check input `123456789` yields `0x29B1`.
- Maximum complete frame length is 128 bytes including `$`, `*`, checksum and LF. Accept CRLF by stripping the single CR before LF; reject any other control/non-ASCII byte, space or empty field.
- Consume bounded input without blocking the control loop; on overlength or malformed input discard until a fresh `$`. A line with an embedded `$` is malformed. CRC validity alone is not authority to execute a request.
- Numerical text is canonical base-10 (no whitespace, leading plus, decimal point, leading zero except `0`, or `-0`). All angles/controls in this UART contract are **command demand**, not measured surface angle.

## State report, Nano → ESP32

```text
$FD1,T,<seq>,<uptime_ms>,<throttle>,<aileron>,<elevator>,<rudder>,<mode>,<rc_link>,<failsafe>*<CRC16><LF>
```

| Field | Allowed values | Meaning |
| --- | --- | --- |
| `seq` | `0..65535` | Increment once per transmitted state frame, wrap to 0 |
| `uptime_ms` | `0..4294967295` | Nano monotonic milliseconds since boot, wraps; not UTC |
| `throttle` | `0..1000` | 0–100% requested throttle in permille |
| `aileron`, `elevator`, `rudder` | `-1000..1000` | Signed normalized control demand in permille |
| `mode` | `MANUAL`, `STABILIZED`, `TAKEOFF`, `CRUISE`, `LANDING`, `FAILSAFE` | Actual onboard mode reported by firmware; support only modes genuinely implemented |
| `rc_link`, `failsafe` | `0` or `1` | Nano-observed receiver state and active onboard failsafe |

Nominal publisher period is 100 ms (10 Hz), subject to flight-control scheduling and bench measurement. A state frame cannot prove physical servo position, verified RC range, sensor health or aircraft readiness. The ESP32 should count valid, invalid, duplicate and skipped frames and publish packet age. Use modulo-65536 sequence arithmetic; a difference of 1 is expected, 0 is duplicate, `2..32767` indicates forward gaps, and `32768..65535` is ambiguous/old until reset is established. `uptime_ms` can help detect a Nano restart, but wraps and clocks are not synchronized.

Set local UART state **STALE** at >1 second after the last valid state frame and **OFFLINE** at >3 seconds. These are proposed thresholds to measure and tune. Preserve a last known value with explicit age; never silently turn a missing axis/sensor into zero. An ESP32 reconnect must not cause a false ACK or silently restore an unsafe command.

## Reserved high-level request, ESP32 → Nano

The v1 framing reserves only an idempotent mode target request, for a later, separately authorized command path:

```text
$FD1,C,<command_id>,SET_MODE,<target_mode>*<CRC16><LF>
```

`command_id` is exactly 16 uppercase hex characters generated by the trusted gateway, unique over the command retention interval. `target_mode` uses the same enum excluding `FAILSAFE` as a web-selected target; the Nano decides which targets and transitions it actually supports. Receipt or valid CRC does **not** authorize the request. The Nano must check local RC/failsafe/transition conditions and leave control local. Unknown command types, modes and unsafe transitions are rejected. The gateway may enqueue a request only after authenticating and authorizing a person through a trusted backend; none of that machinery exists in the current browser milestone.

## Acknowledgement, Nano → ESP32

```text
$FD1,A,<command_id>,<result>,<actual_mode>,<reason>*<CRC16><LF>
```

`result` is `APPLIED` or `REJECTED`. `APPLIED` means the Nano has validated and applied the mode and `actual_mode` names the resulting onboard state. `REJECTED` means no mode change was applied; `actual_mode` still reports current state. `reason` is `OK`, `INVALID_MODE`, `UNSAFE_STATE`, `FAILSAFE_ACTIVE`, or `NOT_IMPLEMENTED`. A duplicate ID should return its cached prior result, if available, without reapplying an effect; a reboot can erase volatile deduplication history. The request is intentionally a target state, not a toggle. Never blindly retry after an ACK timeout because the original may have applied. Use subsequent state telemetry to reconcile actual mode.

| UI/request state | Evidence |
| --- | --- |
| QUEUED | Trusted backend accepted a request; aircraft has not seen it |
| SENT | Gateway wrote the frame, still no aircraft result |
| ACKNOWLEDGED | Matching, valid `APPLIED` acknowledgement and actual state corroborated by a later state report |
| REJECTED | Matching, valid `REJECTED` acknowledgement |
| TIMEOUT / UNKNOWN | No conclusive aircraft result; do not present as success or safe failure |

Command IDs and ACKs need session scoping and audit correlation across gateway/backend restarts. Never let a browser create a trusted ACK. A cloud command system also needs expiry *before* the gateway sends it, and an authorization/revocation check; a Nano cannot compare its `uptime_ms` with an Internet UTC timestamp. Do not use UART CRC as a security signature.

## Reference implementation and test vectors

`firmware/uart_reference.py` is a Python standard-library codec to exercise wire vectors and strict validation; it deliberately does not drive a servo, poll sensors, provision Wi-Fi, or send flight commands. Run:

```bash
python3 -m unittest discover -s firmware -p 'test_*.py'
```

Its test frames are transport examples, not live aircraft data. A Nano/ESP32 implementation should be checked byte for byte against them, then tested for timeout, framing corruption, sequence wrap, reboot, malformed ranges, latency and nonblocking operation on the actual boards.

The literal byte vectors below terminate with LF (`0A`); the visible lines omit that terminator:

```text
$FD1,T,1052,762340,630,50,-40,20,CRUISE,1,0*C7E1
$FD1,C,0123456789ABCDEF,SET_MODE,CRUISE*0203
$FD1,A,0123456789ABCDEF,APPLIED,CRUISE,OK*1BF2
```
